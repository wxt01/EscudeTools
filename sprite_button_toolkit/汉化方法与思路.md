# 标题按钮汉化：方法、思路与工具说明

> 这份文档写给下一个接手这类工作的人或 AI。
>
> **它不是「照着跑就能复现成品」的构建公式。** 脚本是针对本项目几张图的可运行示例，
> 里面的坐标、颜色、字号、阈值只对这几张图成立，换图必须重新量。
> 它真正想给的是：拿到一张陌生的游戏 UI 图时，怎么在几分钟内判断结构、选对工艺、
> 避开已经验证过的坑，并在出问题时快速回退。所以**先读第 0 节的决策树和症状速查**，
> 需要实现时再把 `inspect_sprite.py` 的判据、`repair.py` 的补底函数、
> `layout.py` 的对齐量法搬进你自己的脚本——不必复用本项目任何具体数值。
>
> 记录的不只是「这张图怎么改完的」，更主要是**怎么判断一张陌生的游戏 UI 雪碧图该怎么改**、
> **哪些看似合理的做法会把事情搞砸**，以及**怎么用数值而不是感觉来验收**。
>
> 文中所有具体数值（行高、格子坐标、颜色、字号、辉光强度）都是对原图实测的结果，
> 不是通用常数。建议把「判据、流程、失败教训」当模板带走，把数值留在原地图里重新量。
>
> 文档分三组案例：**第 1~9 节是 `menu_button.png`（透明底发光小字、右对齐）**，
> **第 10 节是设置页七张图**（实心底板、木牌、透明叠加层、装饰笔触、居中），
> **第 11 节是快捷栏 / 右键菜单 / 确认框 / 系统按钮五张图**（透明底、多状态列、
> 白字带辉光、左对齐）。三组结论有冲突的地方（对齐方式、要不要补底、辉光范围），
> 那不是文档自相矛盾，是图的结构不同。先看第 3 节的判据判断你的图属于哪一类，
> 再挑对应路线。
>
> 参数按图片分文件集中：`config.py` / `layout.py` 管标题按钮，
> `config_pages.py` 管设置页三张，`config_frames.py` 管四张框架图，
> `config_batch3.py` 管第三批五张图。

## 0. 三分钟决策卡（先读这个，别先读脚本）

### 0.1 五个问题，问完再动手

| | 问什么 | 怎么量 | 结论指向 |
|---|---|---|---|
| Q1 | 文字背后是透明还是实心底板？ | 看**格间空列**和**原本没字的格**在文字高度的 alpha | ≈0 → A 透明；>200 → B 有底板；中间值先确认是不是半透明面板（10.2 有踩坑） |
| Q2 | 有没有独立的装饰资产？ | 笔触、照片、边框、滑块、黑框 | 有 → 先把「绝对不能碰」的区域写成配置并逐像素核对（10.6） |
| Q3 | **同一行里每格的底色和字色一致吗？** | 逐格算底板 RGB 中位数、文字主色 | 不一致 → 必须逐格量，**绝不按行号写死颜色**（10.4 第 10 条，本轮最贵的坑） |
| Q4 | 原文字怎么对齐？ | 量各格右沿 / 左沿 / 中心哪个恒定 | 照抄：右沿恒定→右对齐到同一缩进；中心恒定→居中；左沿恒定→左对齐（第 3 节、10.5） |
| Q5 | 原文字的发光是什么形状？ | 量字上下的 alpha 剖面 | 只有笔画外 1~3px 有光→贴笔画紧光；字外 10px 仍有 alpha 15~50→整片柔光雾，要字形外扩 + 大半径模糊 |

**Q3 值得单独强调**：本项目 `button.png` 第三行前 9 格是橙黄底深红字，
第 10 格却是青绿底白字。按「第三行 = 深红字」写阈值，那一格的白英文一个像素都没被擦，
直接叠了中文，同时中文还被染成红色。用户一句「英文没删干净就加了中文」把两个症状一起点破。

### 0.2 按结构选工艺

| 结构 | 擦旧字 | 回填 | 重画 |
|---|---|---|---|
| A 透明底 / 发光字 | 整块清成 alpha=0（连辉光一起） | 不需要 | 白字 + 下层描边 + 按 Q5 选辉光；字核心要挖空免得被染成光色。**斜体艺术字是例外**：层序和字体族要按 11.8 重判 |
| B 实心做旧纹理（按钮） | **逐格**以「与该格底板中位色的差异」找文字，膨胀盖住描边/投影 | `patch_repair`：同格干净样本回填，低频取每列中位色、高频取真实残差 | 中文用从该格量到的字色 |
| B 有渐变 / 木纹（木牌） | 同上，mask 保持碎片状，别连成一大片 | `diffuse_repair` 归一化卷积低频 / 或 inpaint；本项目木牌最后也用了同格回填 | 同上 |
| C 透明叠加层（框架图） | 只把文字带清成 alpha=0 | 不需要 | 白字 + 青光；装饰笔触带原样保留 |

**别把 A 的「整块清除」套到 B 上，也别把 B 的「补真实纹理」套到 A 上。**
补底三条已验证的失败模式：填常量色 → 假底板；低频取全图均值 → 偏亮/偏暗的补丁；
平移借用别处高频残差 → 把其它格的字母虚影搬进来（10.4 第 11 条）。

### 0.3 症状速查：用户抱怨 → 大概率原因

| 听到的反馈 | 先查什么 | 详见 |
|---|---|---|
| 「像用亮色把字涂掉了」 | 是不是把旧字笔画填成了背景色、凭空造了底板 | 弯路一 |
| 「字后面有一块亮牌 / 色板」 | 补底填常量、辉光铺成片、外扩半径过大 | 弯路一 / 四、10.4 第 5 条 |
| 「有字形负影 / 暗矩形」 | 顺字形做距离场清除；补底低频取了全图均值 | 弯路三、10.4 第 11 条 |
| **「英文没删干净就加了中文」** | **按行号假设字色 / 阈值只认一种颜色，漏了异色格** | **10.4 第 10 条** |
| **「这个字不该是红色」** | 同上：字色也要逐格从原图量，不要写死 | **10.4 第 10 条** |
| 「多了原版没有的线 / 装饰」 | 把发光边缘或光晕下沿误判成装饰 | 10.4 第 8 条 |
| 「位置很怪 / 字被切掉」 | 没量原图对齐方式就顺手居中 | 第 3 节、10.5 |
| 「字太大 / 太白 / 发虚」 | 只盯放大图调参，没回到 1:1 | 第 7 节 |
| 「汉化后有残留空行 / 某状态没字」 | cy 是绝对 y 还是行内相对 y 混了 | 10.4 第 2 条 |
| 「中文发灰 / 比原字暗一档」 | 衬线/宋体细横画在小字号下抗锯齿把中间调拉低，白字实像素只有原图 1/5 | 11.4 第 1 条 |
| 「又是色板，而且每个词后面一块」 | 汉字是方块字：MaxFilter 外扩、描边、宽辉光会把字间空隙填满 | 11.4 第 3 条 |
| 「字被切掉 / 和旁边的词粘一起」 | 中文字数 × 字号 > 格宽；或按词格分别裁剪辉光，把光切断了 | 11.4 第 5/6 条 |
| 「这一列不该这么亮」 | 禁用态是半透明暗字（原图 alpha 全 <100），被画成了不透明实字 | 11.4 第 4 条 |
| **「原图是斜的，中文变正了」** | 只给了很小的 shear，没量整行基线倾角；「行倾斜」和「字形斜体」是两件事 | 11.8 |
| **「字太粗，风格跟原图差很多」** | 用了粗黑体 + 实心字身；没按原图 alpha 分层，也没挑字体族 | 11.8 |
| **「红白关系反了 / 白字红描边」** | 把「最实的一层」搞错了：这类图描边最实、字身半透明、柔光最淡 | 11.8 |
| **「这个词靠左 / 居中没对上」** | 按词格几何中心居中，没量原字的墨迹中心 | 11.8 |

### 0.4 十条硬纪律

1. 没有底板时**绝不能把旧字笔画涂成背景色**：那等于在字后造一块不透明色块，
   旧字笔画越密越刺眼。正确是整块删除 → 实测背景重建 → 重新渲染。
2. 清除要**整块且均匀**，别顺字形轮廓做距离场，等距线会把字形「印」在背景上。
3. 辉光范围**照抄原图剖面**，别把「只贴笔画」当通用公式（见 Q5、10.4 第 9 条）。
4. 对齐**照抄原图**，别顺手居中，也别一律右对齐——两轮案例答案相反，都是量出来的。
5. 文字颜色、清除阈值**逐格量**，别按行号或状态名假设。
6. 验收同时看 8 倍放大和 1:1：放大图找残影色块，1:1 定最终观感。
7. **先做多状态差分**：把相邻状态列/行逐像素相减。若文字层几乎全等（差异只在图标
   或辉光色），就复用一套字形，别画 N 遍；状态差异用「换辉光色」表达。
8. **辉光强度按原图 alpha 分层校准**，不要凭观感调 gain。把 `>=210 / 140~210 /
   60~140 / 20~60 / 总和` 五档打出来对齐，一眼就知道是过实还是过虚（11.3）。
9. **倾斜拆成两件事量**：整行基线倾角（对墨迹像素做 PCA，或逐行质心拟合）
   和字形本身的斜体（shear）。只做 shear 且系数给小，用户看到的就是「正体字」；
   只做旋转又会把方块字拉歪。中文可用「逐字基线递升 + 整层斜切」分别复现。
10. **对齐基准是原字墨迹中心，不是词格几何中心。** 用户说「对应居中」指的是
    两个中心重合；词格宽度是引擎切的，跟字的实际重心没有必然关系（11.8）。

这次的返工主线：前几轮源于 Q1 看错（用户点名的继续游戏、后日谈、更改设置，
恰好是日文笔画最多、假底最明显的三格）；后来是 Q4 没量；再后来是 Q3 没量；
再往后是「汉字是方块字」带来的新问题（色板、溢出、偏灰）和任务说明与文件不符；
最后一批是**只量了颜色没量「形状与重心」**（斜、粗、红白层序、墨迹中心）。
**结构、颜色、对齐、字形、字数与字号的乘积，都要先量再动手。**

## 1. 任务与素材

| 项 | 内容 |
|---|---|
| 原图 | `原图/menu_button.png`，1092×244，RGBA |
| 结构 | 4 行状态（禁用 / 常态 / 悬停 / 按下）× 7 列按钮，行高 61 |
| 每格内容 | 上方英文大字（CONTINUE 等） + 下方一行日文小字 |
| 特殊 | 禁用行的 CONFIG、QUIT 两格**本来就没有小字**，必须保持全透明 |
| 目标 | 只把日文小字换成中文，其余逐像素不变 |
| 交付 | 同名 PNG 覆盖游戏内 `gfx/sys/title/menu_button.png`，另附对照图 |
| 文案定稿 | 见根目录 `任务说明.md`：继续游戏 / 额外剧情 / 后日谈 / 读取存档 / 更改设置 / 额外内容 / 退出游戏 |

硬约束只有三条：文件名与尺寸不变、保持 RGBA、英文大字与四行状态梯度不动。
字体、字号、辉光强度属于可以调整的审美范畴，没有唯一正确答案；
但**水平对齐方式不是审美选择**，必须照抄原图（本次是右对齐，见第 3 节）。

四行的差别实测下来**不是字形不同**，而是亮度/色相/辉光强度不同，禁用行整体还带半透明。
所以四行可以复用同一套字形与位置，只切换样式参数——这既省事，也保证状态切换时文字不跳动。

## 2. 工具包清单

**这些脚本是「能跑的示例实现」，不是必须照抄的框架。** 路径都基于 `__file__` 相对推导，
整个文件夹拷走能直接跑（字体除外，见 `config.find_font()`）；但接手新图时更常见的用法是
从里面**借判据和函数**：`inspect_sprite.py` 的底板/发光剖面判据、`repair.py` 的两种补底、
`layout.py` 的对齐量法、`verify*.py` 的自检口径，参数和文案全部自己重新量。

| 文件 | 作用 | 什么时候用 |
|---|---|---|
| `config.py` | 全部几何、文案、字体、颜色、强度参数（含右对齐缩进） | 换图第一步就改这里 |
| `layout.py` | 统一布局：按原图右缩进算每词绘制起点，生成与自检共用同一坐标 | 改对齐 / 字距 / 字号时 |

| `build2.py` | 生成成品 + 无字底图 + 2 倍对比样张 | 参数定好之后 |
| `verify2.py` | 交付自检（数值验收） | 每次改完参数 |
| `compare.py` | 1:1 对照、重点格 8~16 倍三栏对照、小字带量化 | 每次肉眼验收 / 定位问题 |
| `_输出/` | 运行产物（无字底图、诊断报告、对照图） | — |

**第二组案例（设置页七张图，详见第 10 节）新增：**

**第三组案例（五张透明底多状态图，详见第 11 节）新增：**

| 文件 | 作用 |
|---|---|
| `config_batch3.py` | 五张图的行列几何、定稿文案、字体、逐列样式、alpha 校准值 |
| `build_batch3.py` | 三种渲染模型：纯白衬线字 / 描边+柔光（带倾斜）/ 白字+青色外发光 |
| `verify_batch3.py` | 30 项自检：清除区外 0 改动、旧字 100% 落在清除区、逐格有字、状态梯度仍在 |
| `compare_batch3.py` | 五张图的 1:1 与 2~4 倍上下对照、popup 全图 1:1 对照 |

依赖：`Python 3` + `numpy` + `Pillow` + 一个中文字体（脚本里有跨平台候选列表）。
**不需要 cv2**：后端固定不自动切换，是为了同一组参数在任何机器上给出一致结果、
便于排查问题，不是要求你复现本项目的成品。想试 inpaint 才需要装
`opencv-python-headless`，那条分支未在成品上验收过。

`_输出/回归基准/` 是**调试用的对照样本**：改动参数后可以快速看出差异落在哪几行几列，
而不是「必须逐像素命中它」。本项目自己重跑能对齐，只是说明这套代码没有隐藏的随机性。

典型顺序：

```bash
cd 工具
# 第一组：标题按钮
python inspect_sprite.py --cols 65:176,345:415,549:619,657:721,774:859,936:985,1004:1084 \
                         --band 31:60 --rows 4 --out _输出/诊断
python build2.py && python verify2.py && python compare.py --pick 0,2,4 --scale 8
# 第二组：设置页 + 框架图
python build_pages.py && python build_frames.py
python verify_all.py
python compare_pages.py && python compare_frames.py
# 第三组：透明底多状态图
python build_batch3.py && python verify_batch3.py && python compare_batch3.py
```

`inspect_sprite.py` 不给 `--cols` 时会只做全图剖面并打印非透明连续段，
适合还没定位格子的阶段；`compare.py` 的 `--pick` 换成别的格序号、`--scale` 调到 16，
就能盯住某一格反复看。

`_输出/回归基准_成品.png` 是本次定稿（右对齐版）成品的副本；
`_输出/历史_居中版.png` 是修正对齐之前的居中版，留作前后对照。
改完参数想确认「没把别处改坏」时，
可以直接和新输出做逐像素比对；如果只想调整某一格的样式，
比对结果会精确告诉你改动落在哪一行哪一列：

```python
import numpy as np
from PIL import Image
a = np.array(Image.open("_输出/回归基准_成品.png").convert("RGBA"))
b = np.array(Image.open("../交付成品放这里/menu_button.png").convert("RGBA"))
d = (a != b).any(axis=2)
ys, xs = np.where(d)
print("不同像素:", int(d.sum()),
      "范围 x", (int(xs.min()), int(xs.max())) if d.any() else None,
      "y", (int(ys.min()), int(ys.max())) if d.any() else None)
```

`_输出/诊断/` 里留了一份本次的诊断报告和四张诊断图，可以直接当示例输出看。

## 3. 第一步永远是结构诊断，不要先动笔

人眼很容易把「文字的辉光」看成「一条发光底板」，尤其在 2~4 倍放大、
又叠加了英文大字下缘余光的情况下。所以诊断要靠 alpha 数值。

`inspect_sprite.py` 建议你关注四组量：

- **行数与行高**：`H / 状态数`，再用每行的非透明像素分布确认行边界没有偏移。
- **每格 x 范围**：文字带内的列投影，找连续非透明段；范围可以略宽于真实字形。
- **小字带 y 范围**：逐 rel y 看全行 alpha 中位数。大字下缘辉光会缓慢衰减，
  小字会让某一段明显抬高。本次量到行内 rel 31 以下基本只剩大字余光，
  小字主体在 35~54，所以清除窗口取 31~60。
- **状态差异**：逐格数「白色实像素」「青色像素」。若各行白字数量接近、
  只有青光和亮度递增，就说明字形是复用的，样式才是变量。

### 底板判据（整套方法的分水岭）

看两个位置在文字带高度上的 alpha：

1. 所有格子范围之外的「格间列」；
2. 原本就空白的格子（本次是禁用行 CONFIG / QUIT）。

本次实测输出：

```
行0 格间列 alpha: 中位 0 最大 97 均值 7.7
行0 空白格4 alpha: 最大 0
行0 空白格6 alpha: 最大 0
行1 格间列 alpha: 中位 0 最大 193 均值 15.9
...
```

格间列中位数为 0、空白格最大值为 0 → **没有底板**。
（最大值不为 0 是英文大字下缘辉光的横向余晖，属正常；看中位数和空白格更可靠。）

这个结论直接决定技术路线：

| 判据结果 | 结构 | 建议做法 |
|---|---|---|
| 格间/空白格 alpha ≈ 0 | 字与辉光悬空 | 整块清除 + 真实背景重建 + 重画（本次） |
| 格间/空白格 alpha 明显 > 0 且横向连续成带 | 真有底板 | 改动可以小很多：保留底板，只在底板范围内替换字形；注意保留底板渐变 |

顺便一提：如果底板带渐变或纹理，「取中位数背景」就不够了，
需要按列插值、从相邻行采样，甚至做简单 inpainting。这时候别硬套 `build2.py` 的第 3 步。

### 水平对齐判据（第二个分水岭）

结构搞清楚之后，第二件必须量的事是**旧字的对齐方式**。别看到「一小行字」就默认居中。

做法：在常态行的文字带里取每格白色实像素的 x 最小/最大值，
算出「右沿到格右线的距离」和「左沿到格左线的距离」。本次实测：

| 格 | 日文白字 x 范围 | 宽 | 右沿距格右线 | 左沿距格左线 |
|---|---|---|---|---|
| 继续游戏 | 69..172 | 104 | 4 | 4 |
| 额外剧情 | 349..411 | 63 | 4 | 4 |
| 后日谈 | 553..615 | 63 | 4 | 4 |
| 读取存档 | 661..717 | 57 | 4 | 4 |
| 更改设置 | 778..856 | 79 | 3 | 4 |
| 额外内容 | 940..982 | 43 | 3 | 4 |
| 退出游戏 | 1020..1080 | 61 | 4 | **16** |

右缩进全部是 3~4px（改用「含描边、alpha>200」的判据则**恒为 2px**），
而左缩进差异巨大，最后一格甚至空出 16px —— 这是**严格右对齐**，不是居中，也不是两端拉伸。

推论：新文字必须右对齐到同一缩进。中文和日文宽度不成比例，居中时各格末尾会随字数乱跑：
本次「继续游戏」中文只有 67px 宽、缩在格中间（87..153），
而「额外内容」中文约 70px 却比日文 43px 长得多，右端冲到约 996，
越过格右线 985 达 11px，在游戏里被切掉。

实现上别用 `textlength` 估算：逐字绘制带字距和 1px 描边时，
理论宽度与真实像素外沿会差 1~2px，七格各差一点，末尾就对不齐。
`layout.py` 的做法是**先以 x=0 渲染一个探针图层、量出真实外沿，再整体平移**到
`COLS[ci][1] - RIGHT_INSET`；`build2.py` 和 `verify2.py` 都调用同一个
`word_starts()`，避免自检拿旧坐标去查残留而误报。

右对齐后中文会往左伸（「额外内容」左沿到 912），
所以**清除区左界也要跟着中文实际左沿扩展**（`CLEAR_PAD_EXTRA`），
否则中文会压在没清干净的背景上。扩展后应复查格间区域亮度是否回到原图水平
（本次该区 alpha 均值：原图 23.4 / 居中版 66.0 / 右对齐版 20.7，越界亮块随之消失）。

## 4. 走过的弯路（这部分最值得看）

### 弯路一：把「擦字补底」当成方案（v1，被用户明确否掉）

- **假设**：日文小字压在一条半透明青色发光带上。
- **做法**：识别日文白色笔画，只把这些像素的 RGB 换成同高度背景色，alpha 压到发光带峰值 234。
- **为什么错**：根本没有那条带。填进去的 234 不透明青色是凭空造的亮牌，
  而且笔画越密，亮牌连成的面积越大。
- **症状**：继续游戏（日文 8 字）、后日谈（笔画密）、更改设置三格出现明显亮青色块；
  字数少的格子反而看着还行，很有迷惑性。
- **教训**：**擦除法只在「字下面确实有可复原的底板」时成立**。
  悬空文字没有可复原的「下面」，擦完只会留下字形的负空间。

### 弯路二：用拟合模型重建背景

- **做法**：测一条发光带的 y 钟形 alpha 剖面，用它反推被字遮住位置的 alpha。
- **为什么错**：那条剖面本身就是「文字辉光 + 大字余晖」的混合，不是背景模型；
  按模型填出来的区域过于均匀且偏亮，仍然是一块板。
- **教训**：背景要从**原图同一行、同一高度、同类区域实测**，别用公式生成。

### 弯路三：按字形做连续距离场清除

- **做法**：以旧字笔画为种子算距离场，距离越远越保留原图，期望得到平滑过渡。
- **为什么错**：距离场的等值线就是字形的膨胀轮廓，等于把字形「印」在了背景上，
  出现暗矩形和日文负影；膨胀半径调大调小只是换一种轮廓。
- **教训**：清除区域的形状必须**与字形无关**，内部要完全均匀，只在四周羽化。

### 弯路四：线性叠加宽半径辉光

- **做法**：把文字层高斯模糊后按强度直接叠成青光。
- **为什么错**：模糊后整片区域 alpha 普遍 220+，等于又垫了一层暗青底；
  汉字笔画密，多个字的模糊核互相叠加，糊成一整片方雾。
- **教训**：模糊 alpha 要做**幂次压缩**（`alpha^p`，p>1），把字间低值压到接近 0，
  只留紧贴笔画的一圈；必要时再加一层极淡的远光。

### 弯路五：逐词单独算基线

- **做法**：每个词用自己的 `textbbox` 算垂直居中位置。
- **为什么错**：不同字符的 bbox 下沿不一致（「谈」bottom=20、「续」bottom=18 之类），
  导致不同格之间最多 0.5px 的上下浮动。用户看到「谈」有点偏上，
  实测三字基线其实完全一致、整格相对日文还偏下 0.4px——
  真正原因是 15px 下「谈」笔画多、抗锯齿让捺脚淡没，视觉上上重下轻。
- **教训**：垂直位置用**全部字符 bbox 并集**算一次，全图共用；
  复杂字的「发虚」和「错位」是两回事，先量质心再决定改哪个。

### 弯路六：默认居中（用户最后一轮指出的）

- **假设**：小字短，放在格子中间最稳妥。
- **做法**：`x = (x0+x1)/2 - tw/2` 逐格居中。
- **为什么错**：原图是严格右对齐（见第 3 节）。中文字数与日文假名数不成比例，
  居中会让各格末尾位置随字数漂移，看起来「这一格跟别的不一样」；
  字数相对多的格还会越出右边界被裁。
- **症状**：「继续游戏」缩在中间显得突兀；「额外内容」右端超出格右线约 11px。
- **教训**：对齐方式是原图的**结构属性**，不是可以自由选择的排版偏好。
  量右缩进 → 右对齐 → 用探针图层量真实外沿 → 清除区跟着中文左沿扩展。

### 归纳成四条原则

1. 清除要整块且均匀，别让清除区携带任何字形信息。
2. 背景必须实测，别拟合、别填常量。
3. 辉光要贴笔画；低 alpha 不压没，就一定会变成底板。
4. 新文字照抄原图的对齐方式；右对齐时清除区要跟着中文左沿扩展。

## 5. 最终方案

数据流：

```
原图 RGBA
  │
  ├─ 1. 整块清除：每格 [min(x0-14, 中文左沿-8), x1+15] × 行内 rel 31..60
  │      左右 9px 线性羽化，上下按辉光衰减给权重，内部 keep=0
  │      左界跟着中文实际左沿扩展，保证右对齐后的中文落在干净背景上
  │
  ├─ 2. 背景重建：对每个 (状态行 r, 行内高度 rel)
  │      取「所有非小字列」像素的 RGBA 中位数，按 keep 线性混合
  │      → clean_base.png（无字底图，单独留档）
  │
  ├─ 3. 重画中文（每行一个透明图层）
  │      冷白字 + 1px 深青描边 + 统一基线 + 字距 + 右对齐到日文末尾
  │      两层外发光（近亮远淡，模糊 alpha 做幂次压缩）
  │      文字层 alpha × 1.35 补实细笔画
  │      整层用 win 窗口裁到 rel 30..60，上下羽化
  │
  └─ 4. alpha_composite：底图 → 辉光层 → 文字层
         → 成品 PNG（四行字形与位置完全相同，只换 tint / glow / alpha）
```

几个实现选择及其理由：

- **用中位数而不是均值取背景**：非小字列里偶尔混着大字辉光的亮边，
  中位数对这种离群值更稳，取出来的背景更干净。
- **按「行 × 高度」分别取背景**：大字下缘辉光在 y 方向衰减很快，
  整行用一个常量会在上下缘出现水平断层。这是消除「横向断层」的关键。
- **清除边界推到离文字足够远**：右界 `x1+15`，左界 `min(x0-14, 中文左沿-8)`，
  都落在辉光已衰减到 0 的地方，羽化发生在几乎全透明的区域，肉眼看不见边界。
  右对齐后中文比日文长的格子（额外内容）左沿会明显外移，左界必须跟着走。
- **水平位置用探针图层实测外沿**：`layout.word_starts()` 先以 x=0 逐字渲染、
  量出含描边的真实右外沿，再平移到 `COLS[ci][1] - RIGHT_INSET`。
  不用 `textlength` 估算，是因为字距和描边会让每格差 1~2px，末尾就对不齐；
  生成与自检共用这个函数，也避免坐标不一致导致残留检测误报。
- **合成顺序 底图 → 辉光 → 文字**：文字层最后叠，
  保证白字笔画不被辉光染青；文字层的加实也只在自己那层做，不影响已算好的辉光。
- **禁用行只改文字层 alpha**：原图禁用态是整体偏暗偏淡，
  用 `TEXT_ALPHA` 缩放文字层比改颜色更接近原味；CONFIG / QUIT 两格直接跳过不画。
- **四行共用一个 `PY` 和一份字形**：状态切换时文字不位移，
  这也是游戏里鼠标划过时观感自然的前提。

`config.py` 里 `GLOW_LAYERS` 的 `power`、`TEXT_ALPHA_BOOST`、`OUTLINE_ALPHA`、
`win` 窗口那几行羽化值，属于「针对这套字体/字号调出来的手感参数」，
换字号或换字体后建议重新对着原图小字挑一遍，不用当成公式。

## 6. 参数速查与调参手感

| 参数 | 影响 | 调大 / 调小 | 换图是否必须重测 |
|---|---|---|---|
| `W,H,ROW_H,N_ROWS,COLS` | 几何骨架 | 错了会整片错位 | 必须 |
| `BAND_TOP/BOTTOM` | 清除与新图层的 y 范围 | 太窄留残影，太宽会碰到英文大字 | 必须 |
| `TEXT_CY` | 中文垂直位置 | 往上/下整体移动 | 必须 |
| `ROW0_EMPTY` | 哪些格保持空白 | 漏了会凭空多出小字 | 必须 |
| `CLEAR_PAD_X, EDGE` | 清除区外扩与羽化 | 太小露边界，太大可能吃掉邻格 | 建议 |
| `FONT_SIZE` | 视觉重量 | 大＝更实但显得笨重；小＝精致但复杂字发虚 | 建议 |
| `CHAR_GAP` | 字距 | 大＝笔画间能透黑、光晕不糊；太大则松散 | 建议 |
| `RIGHT_INSET` | 中文右沿到格右线的缩进 | 必须与日文实测一致；大了整体偏左，小了贴边 | 必须 |
| `ALIGN_ALPHA_THRESHOLD` | 量字形外沿用的 alpha 阈值 | 太大漏掉描边，太小把抗锯齿毛刺算进来 | 建议 |
| `CLEAR_PAD_EXTRA` | 清除区左界相对中文左沿的外扩 | 太小中文压在脏背景上，太大抹掉邻格余晖 | 建议 |
| `GLOW_GAIN` | 每行光强 | 大＝更亮但容易连成青板 | 建议 |
| `GLOW_LAYERS` 的 `power` | 光的贴合度 | 越大越只贴笔画，越不像板 | 建议 |
| `TEXT_TINT/OUTLINE/GLOW_RGB` | 颜色 | 建议直接从原图小字笔画取色 | 建议 |
| `TEXT_ALPHA_BOOST` | 细笔画补实 | 过大字会发胖 | 可选 |
| `TEXT_ALPHA` | 禁用态整体浓度 | 与原图禁用行比对着给 | 视状态数 |

调参经验：

- **一次只改一类参数**。同时动字号和辉光，出问题就分不清是谁造成的。
- 顺序建议：先让「无字底图」干净 → 再让中文白字清晰 → 最后调辉光强度与范围。
- 每改一次跑 `compare.py`：先 8~16 倍确认没有残影/色块，再 1:1 看整体是否协调。
- 想更亮就提 `GLOW_GAIN`，但每提一档都要回 8 倍图确认光没有连成片；
  想更精致就降 `FONT_SIZE`，但要先检查「谈」「戏」「续」这类多笔画字有没有糊。
- 对齐不是调参项：先按第 3 节量出原图右缩进，写进 `RIGHT_INSET`，
  让 `layout.py` 统一算位置。若原图其实是居中或左对齐，改 `layout.word_starts()`
  里的目标公式即可，但别在 `build2.py` 里逐格硬编码。
- 改了 `FONT_SIZE` / `CHAR_GAP` / 字体之后各词宽度会变，
  `word_starts()` 会自动重算右对齐起点；但要重新检查最长的词有没有顶到相邻格。

## 7. 验收：别只靠「看起来还行」

### 定量（`verify2.py`）

| 检查 | 意义 |
|---|---|
| 尺寸 / RGBA | 游戏能否直接读取、覆盖 |
| 小字带以外 0 像素改动 | 英文大字和其余辉光确实没被碰 |
| 每格中文笔画像素 > 60 | 没有漏字 |
| 四行共有格包围盒完全对齐 | 状态切换不跳动 |
| 每格中文白字右沿 vs 日文白字右沿差 ≤ 2px | 末尾缩进与原图完全一致 |
| 中文白字右沿不越过格右线 | 字不会被游戏切掉 |
| 中文笔画之外无白色实像素 | 旧字没有残留 |
| 禁用行空白格与原图逐像素一致 | 不该出现的小字没冒出来 |
| 青光像素逐行递增 | 四态梯度保住了 |

两个口径上的坑，写下来免得重踩：

- 禁用行少了两格中文，**不能拿整行包围盒互比**，只能比共有格；
- 空白格左右各 14px 是相邻格的清除羽化余量，
  检查「空白格是否原样」时只看本格 x 范围，否则会误报；
- 相邻格可能很近（本次 EXTRA 右线 985 / QUIT 左线 1004 只隔 19px），
  用「格中心 ± 固定窗口」统计会把隔壁格的字算进来，
  得出「某格中文宽 88px」这种假数据。末尾检查应在本格右侧小区间内
  只取白色实像素的最大 x，或直接用 `layout.word_starts()` 的已知起点。

### 定性（`compare.py`）

- **三栏对照**（原图 / `clean_base.png` / 成品）是最高效的定位工具：
  底图脏 → 清除步骤的问题；底图干净但成品怪 → 渲染参数的问题。
- **8~16 倍**：找字形负影、涂抹块、矩形轮廓、水平断层、辉光糊成板。
- **1:1 真实尺寸**：最终拍板。放大会放大「字太粗太白」的错觉，
  本次就曾在 1:1 下发现中文比原图日文重了一档，又收小了一号字。
- **量化指标**（白色实像素、青光像素、白字质心 y、包围盒）只用来做前后相对比较，
  没有绝对及格线。比如本次成品青光像素低于原图，是有意收敛以避免糊成板，
  不代表「不合格」。

### 环境里做不了的部分

把成品覆盖回游戏后，实际用鼠标划过、按下按钮，确认四种状态切换时
中文不露旧字、辉光过渡自然。这一步脚本替代不了，必须真人验收。

## 8. 迁移到别的图 / 别的任务

建议的工作流：

1. `inspect_sprite.py` 跑一遍，拿到行数行高、格子坐标、文字带 y 范围。
2. 用底板判据决定路线（悬空 → 删除重画；有底板 → 局部替换）。
3. 从原图小字笔画取色：白字色、描边色、辉光色；数一下各行白字/青光像素，
   判断状态差异是「亮度」还是「字形」；**顺便量每格右缩进、确定对齐方式**
   （见第 3 节），把缩进写进 `RIGHT_INSET`。
4. 把几何与文案写进 `config.py`，先跑 `build2.py` 出无字底图，
   **只检查底图干净不干净**，别急着看成品。
5. 再调字体与辉光，循环 `build2.py → compare.py → verify2.py`。
6. 最后 1:1 拍板，交回游戏里实测四态。

可以直接照抄的部分：整块清除 + 羽化的框架、按「行 × 高度」取中位数背景的做法、
辉光幂次压缩、统一基线、探针图层量外沿做右对齐、四行复用字形、整套自检框架。

必须重新量/重新调的部分：所有几何量、颜色、状态数与状态含义、字体与字号、
清除窗口与羽化形状、右缩进量与对齐方式。

几种常见变体的处理思路：

- **确实有底板**：别套「整块清除」。保留底板（含渐变），
  只在底板范围内把旧字笔画换成底板色，再把新字画上去，改动量小得多。
  若底板有渐变，替换时按该 x 列上下取样插值，不要用单一颜色。
- **状态数不是 4**：`GLOW_GAIN` / `TEXT_TINT` / `GLOW_RGB` 这些字典的长度跟着改；
  `verify2.py` 里的「逐行递增」断言也要按实际状态含义调整（有的图第 2 行是按下、第 3 行是悬停）。
- **字数差别大 / 中英混排**：先照抄原图的对齐方式（多半是右对齐或居中其一）。
  若新文字明显比旧文字长，右对齐会往左伸，此时检查清除区是否跟着扩展、
  有没有顶到相邻格；居中则要检查两端是否越界。实在放不下再考虑缩字号或减字距，
  别靠改对齐方式硬塞。
- **没有微软雅黑 / 换平台**：`config.find_font()` 里补本机字体路径。
  换了字体几乎一定要重调 `FONT_SIZE`、`CHAR_GAP`、`TEXT_ALPHA_BOOST`，
  并专门挑几个笔画最多的字放大检查。
- **PNG 是索引色 / 带调色板**：先 `convert("RGBA")` 再处理；
  交付前确认游戏是否要求特定格式，必要时转回去并验证透明色没被破坏。
- **文字带和英文大字在 y 方向重叠**：`BAND_TOP` 不能简单往下移，
  需要考虑按格局部清除、或从相邻状态行借背景，改动会明显变大。

最后一句提醒：`config.py` 里那些数值是「这张图的答案」，不是「这类题的公式」。
真正可迁移的是第 3 节的两个判据（底板、对齐）、第 4 节的教训和第 8 节的流程。

### 10.2 七张图其实是四种结构

| 图 | 字背后是什么 | 怎么量出来 | 技术路线 |
|---|---|---|---|
| `index.png` | **透明** + 白字带彩色外发光 | 格间列 alpha<6、第 3 行第 6 格全 0 | 与 `menu_button` 同类：整行清成透明，重画字 + 外发光 |
| `button.png` | **实心做旧底板**（青绿 / 橙黄） | alpha 均值 254.7、最小 6、无透明像素 | 擦字后**必须补回真实纹理** |
| `title.png` | **木牌亮黄斑驳纹理** + 深棕烙字 | 木牌内部 alpha=255，文字是深棕不是白 | 同上，但纹理更强、面积更大 |
| `frame_*.png` | **透明叠加层** + 独立青色水彩笔触 | 文字带背景样点 `(255,255,255,0)` | 只把文字带清成透明，笔触逐像素保留 |

**这一轮最容易看错的是最后一种。** 用深灰底合成出来做预览时，
`frame_*.png` 看起来像「深色实心面板上写着白字」，很容易当成不透明底图去补背景。
但直接读 alpha 就会发现那片深色是**你合成上去的**，原图里是 alpha=0，
深色背景是游戏运行时另画的。判据很简单：

```python
a = np.array(Image.open(p).convert("RGBA"))
print(a[y_text_band, x_gap, 3])     # 文字带里、格间空列的 alpha
```

是 0 就不要补底板，补了反而会在游戏里露出一块颜色不对的补丁。
**永远读 alpha，别看着预览图下结论。**

补一个好用的辅助判据：把「字周围半透明像素」的颜色做个众数统计，
能直接量出原图辉光的真实色。这次量到三行分别是 `(0,120,136)` 深青、
`(0,220,200)` 亮青绿、`(240,16,0)` 红，比我一开始挑的蓝色准得多。

### 10.3 有底板时怎么补（第 4 节教训的延伸）

第 4 节说「背景必须实测」，在实心底板上要再进一步：**背景必须保留纹理**。
做旧金属、木牌这类底板是高频斑驳，人眼对「一块均匀色」极敏感，
哪怕平均色完全正确，也会看成补丁。

三条路（`repair.py`），按底板纹理类型选，别混着用：

1. **`patch_repair` 同格纹理回填（本项目最终用的）**：低频取「该格每列 mask 外像素的
   中位色」，高频从该格干净像素的真实残差里确定性取样。适合统计平稳的做旧纹理
   （按钮、木牌）。大片整词擦除也不会补出偏亮或偏暗的矩形。
2. **`diffuse_repair` 归一化卷积低频 + 少量松弛**：只用 mask 外真实像素插值出局部底色，
   再补一点颗粒噪声。适合有大尺度渐变、同格样本不足以代表整体的底板。
   ★ 初值绝不能用全图均值（多状态图各行底色差很大），见 10.4 第 11 条。
3. **OpenCV inpaint（Telea，可选）**：沿等照度线推进真实纹理，细笔画很干净；
   但未在本项目成品上验收，装了 cv2 也别让它自动接管。

三个要点：

- **mask 逐格自适应，别按行号或状态名写死颜色**：先取该格底板 RGB 中位数，
  再用「与该格底色的绝对差之和 > 阈值」找文字，亮字、深字、投影一起抓。
  本项目曾写「第 3 行 = 深红字 `R > G*1.55`」，结果同行最后一格是白字、
  整格英文漏擦（10.4 第 10 条）。**文字主色也从该格量出来给中文用。**
- **mask 别做成整块矩形**：笔画之间的原始底板是最宝贵的纹理来源。
  但整词擦除时膨胀后自然会连成片，这时靠 `patch_repair` 兜住，不是靠缩小 mask 硬躲。
- 膨胀是为了盖住描边和抗锯齿过渡带。漏了就会留下字形负影
  （这次 `button.png` 第一版就残留了 OFF / NORMAL 的横向笔画，放大看像 `===`）。

`texture.py`（整行平移复制真实纹理）是早期尝试，**已弃用**：
逐行从不同源行取样会产生行间颜色跳变，在木牌上表现为一片横向条纹。
留在工具包里当反面参考，别直接拿去用。

### 10.4 这一轮新踩的坑

按「症状 → 原因 → 改法」记，基本都跟**细笔画 + 发光**有关：

1. **白字变成暗色空心字。**
   `PIL` 的 `stroke_width=1` 在宋体小字号上会吃掉 1~2px 的实笔画，
   只剩深色描边可见。改成**描边层与实字层分开渲染**：先画带 2px stroke 的实心描边层，
   再在上面画无 stroke 的白色实字层覆盖。文字层 alpha 再 ×1.25~1.45 加实。
2. **后两行整个没有字。**
   `cy` 到底是「绝对 y」还是「行内相对 y」没统一，代码又加了一次行起点，
   结果第 2/3 行被画到图片外面。**自检必须按行分别数像素**，
   只检查「整图有白字」会完全漏掉。
3. **外发光等于没有。**
   只对文字 alpha 做高斯模糊，字外 1px 的 alpha 只有个位数。
   改成「字形外扩（MaxFilter）+ 模糊 = 紧光」再叠「大半径柔光」。
4. **白字被染成蓝色。**
   发光层盖在半透明的细笔画上，白字混成了光色。
   加一句 `ga *= (1 - core_alpha * 0.98)` 挖空字核心，光只在字外。
5. **光晕糊成实心色板。**
   外扩半径 7px 时，汉字笔画密、字间空隙被填满，整词连成一块亮青。
   收敛到 `expand=5 / tight_w=0.52`，并且**验收同时看 2x 和 1:1**。
   （第 4 节那条「低 alpha 不压没就变底板」在这里换了个形式重现：
   这次是「高 alpha 铺太宽」变底板。）
6. **新图层蹭掉装饰笔触。**
   `frame_manual` 的绿色键位行紧跟在青色笔触下面，
   允许区域向上外扩 4px 就把笔触尾部一起改了。
   改成**只向左右和下方外扩**，上方绝不扩。
7. **自检口径写错三次**（值得单独看）：
   - 「清除带外 0 改动」对有底板的图不成立——新中文笔画本来就在原英文 mask 之外。
     正确口径是「**显著改动**（RGB 差 >40）必须落在预期文字矩形内」。
   - 笔触带不能由「每条 clear 的 `y1+N`」推算，因为键位行紧跟标题会被误算成笔触。
     用实测的 `BRUSH_BANDS` 显式写死，再逐像素核对。
   - 「带外改动数」里混进了新文字的抗锯齿过渡（±1~16），
     别用「有改动」判失败，用幅度判。
8. **凭空给红态加了一条下划线。**（用户直接指出：「原版没有的」）
   第三行（选中/红态）的红色在字上下都有，放大预览里下沿连成一条，
   被误判成「红色下划线」，于是额外画了 2px 实心红矩形贴在字底。
   回原版逐行量才发现：**那是一整圈柔和外发光**，剖面是
   字上 10px 处 alpha≈50、贴近字 ≈120、字下 10px 又衰减到 ≈15，
   边缘模糊、根本没有清晰直线。**教训：任何「原图有 XX 装饰」的判断，
   都要有数值剖面或清晰的放大证据，别靠预览图的整体印象。**
   删掉画线代码后，`verify_all.py` 增加了一条回归判据
   「第 3 行不存在长度 ≥20px 的高不透明纯红横段」，把这条反馈固化下来。
9. **把「辉光只贴笔画」绝对化，三行都暗了一档。**
   为防色板把发光收得太紧：原版彩色光像素约 12200 / 行，成品只有 5000 左右，
   字上方 8px 处原版 alpha 52、成品 3。于是按词补柔光：
   - 先试「按词包围盒画矩形 + 模糊」→ 每个词后面能看出一块**圆角矩形光板**，
     正是第 4 节批评过的东西，弃用；
   - 改成「**字形外扩（MaxFilter 11）+ 大半径模糊（6）**」→ 边缘跟随字形起伏，
     剖面接近原版（20→75→21 vs 原版 20→120→15），且没有矩形直边。
   参数在 `config_pages.py` 的 `INDEX_HAZE`，`alpha=0` 可整体关掉。
   **同一种「发光」在不同图上可能是两种完全不同的结构，先量剖面再选实现。**
   另外这里踩了个低级坑：新参数起名 `INDEX_BAND`，和已有验收口径的同名 tuple
   （`(2, 46)`）撞车导致 `TypeError`，改名 `INDEX_HAZE`。配置里加参数前先搜一下名字。
10. **按「第几行」假设底色和字色，整格英文漏擦、中文还染错色。**（本轮用户指出）
    `button.png` 第三行被认为是「橙黄底 + 深红字」，于是擦字阈值写成
    `R > G*1.55 且 G < 135`（找深红）。但**第三行第 10 格 SETTING 是青绿底 + 白字**，
    一个像素都不满足深红条件 → 英文完整保留，红色中文直接叠在 SETTING 上。
    用户一句「第三个应用并不是红色的字，而且你英文也没有删干净就加了中文」，
    两个症状其实是**同一个原因**。
    - 正确做法：**逐格**取该格文字带 RGB 的中位数当底板色，
      用「与该格底色的绝对差之和 > 阈值」找文字（亮字和深字都能抓），
      再从「差异最大的那部分像素」的中位数取**文字主色**，中文就用这个颜色。
    - 本项目量出来：第 1 行 10 格全 `(255,255,255)`；
      第 3 行前 9 格 `(175,12,0)`、第 10 格 `(255,255,255)`。
      配置里保留的 `BUTTON_STYLE` 只作量不到时的兜底，不再决定成品。
    - **通用教训**：状态行 ≠ 统一配色。特例按钮（确认/应用/返回）、
      禁用态、选中态都可能在同行里换皮。任何「第 N 行一定是 X 色」的假设，
      都要先逐格打印中位数验证。自检也别只查「整图有没有字」，
      要**逐格**确认原文字像素确实被改动过。
11. **补底的三种失败模式，以及最后有效的那种。**
    整词擦除后 mask 连成一大片，最考验补底：
    - **全图均值初始化 + 几百次扩散** → 多状态雪碧图各行底色差别很大，
      擦除区被补成一块偏亮、发平的补丁（第 4 节「涂抹感」换了形式重现）。
    - **归一化卷积低频**（只用 mask 外真实像素插值出局部底色）→ 亮暗对了，
      但 mask 四周剩下的参考像素常是按钮的暗边，大片区域仍会偏暗成矩形。
    - **平移借用别处的高频残差**来补做旧纹理 → 会把**其它格子的文字残差**
      一起搬进来，擦除区出现 `TTI` 之类的字母虚影，比原来更糟，弃用。
    - ✅ **同格纹理回填（`patch_repair`）**：低频取「该格每一列中 mask 外像素的
      中位色」（保住水平渐变和真实亮度），高频从该格干净像素的**真实残差**里
      确定性取样（保住做旧颗粒，取样用固定公式而非随机数便于排查）。
      边界 1px 半混合消硬边。按钮和木牌最终都用它，1:1 下看不出补丁。
    **判据**：底板是统计平稳的做旧纹理 → 同格回填；有明显大尺度渐变/木纹 →
    归一化卷积或 inpaint；透明底 → 根本不需要补底。
    对应 0.2 的路线表，别三种混着用。

### 10.5 居中还是右对齐，由原图决定

两轮任务给出了相反答案，正好说明**这不是偏好问题，是测量问题**：

| 图 | 原文字怎么排 | 结论 |
|---|---|---|
| `menu_button.png` | 日文右沿距格右线恒 2px，左沿差异很大 | **右对齐** |
| `index / button.png` | 英文词中心 ≈ 格中心 | **居中** |
| `frame_*.png` 设置项 | 三列中心固定 220 / 640 / 1058 | **居中**于列中心 |
| `frame_manual` 键位行 | 原本左对齐于 x=43 / 461 / 879 | **保持左对齐** |

用户第二轮说「这次居中会比较好」，是个有用的提示，但别当成规则套用。
量法：对每行每格取原文字的白色笔画左右边界，看**右沿是否恒定**（右对齐）、
**中心是否恒定**（居中）、还是**左沿是否恒定**（左对齐）。
同一张图里不同元素可以有不同的对齐方式（标题居中、键位行左对齐），
关键是「跟原图一致」，而不是「全图统一用一种」。

### 10.6 保护非文字资产

这轮第一次遇到「图上有必须逐像素保留的装饰」和「明确不译的元素」：

- **青色水彩笔触**：文字带与笔触带在 y 上不重叠（文字底 +3px 之后才是笔触）。
  清除窗口止于文字底 +3px，新图层再用 `allow` 掩码裁在窗口附近。
  自检用 `BRUSH_BANDS` 对这些像素做**逐像素全等**检查
  （四张分别 2.7 万 / 3.6 万 / 2.6 万 / 1.5 万像素，全 0 差异）。
- **BGM / BGV 两格**：连清除窗口都不给它，直接保持原图像素，自检核对全等。
- **键名**：因为同一行的标签「キーボード」要译，整行得重画，
  所以键名是「原样写回」而不是「保留像素」；自检用文案断言五个键名都在。
- **`frame_text` 顶部照片、底部黑框**：自检核对 `y<115` 与 `y>560` 完全未动。

通用做法：**先把「绝对不能碰的区域」列成显式配置，再写自检逐像素核对**，
比事后靠眼睛找划痕可靠得多。

### 10.7 这一组的运行顺序与验收

「button 30 格旧英文全部被擦除」（10.4 第 10 条，逐格数 mask 覆盖量，漏擦时接近 0）。

这次 `index.png` 的光晕就是在 2x 下调过头、又收回来一次的。

### 10.8 关于后端选择与一致性

`repair.py` 里 `USE_CV2 = False` 是故意固定的：后端不随「这台机器装没装 cv2」自动切换，
同一组参数在任何环境给出一致结果，排查问题时才不会被环境差异干扰。
**这不是要求你复现本项目成品**——`_输出/回归基准/` 只是调试时的差异对照样本。

当前分工：`button / title` 走 `patch_repair`（同格纹理回填）；
`diffuse_repair`（归一化卷积低频）和 OpenCV inpaint 保留作备选，
适用于底板有明显大尺度渐变、同格样本不足以代表整体的情况（见 10.4 第 11 条）。
换图时按 0.2 路线表选，**选完一定出一张 1:1 上下对照和一张 8 倍局部放大再定稿**。

## 11. 实战案例三：透明底多状态图（五张）

> 第三批五张：`radio_button`（585×217，3 列 × 7 行）、`check_box`（606×450，

### 11.1 任务说明也可能写错，以文件为准

`任务说明.md` 追加任务三说 `popup_parts.png` 是「只有左上 x 0..155、y 52..396，
8 项竖排」。实测文件是 **4 列状态 × 9 行**、文字分布在 x 50/266/482/698 四处：

- 列 0 暗褐禁用态（alpha 全 <100）、列 1 米白字 + 深褐描边、
  列 2/3 红/橙红描边 + 白色外发光，且列 2/3 每行左侧另有**红色箭头**；
- y 0..43 还有一行 `FLOWCHART`，说明表格里没列（文档只从 y 52 开始写 8 项）。

按文档只改 x 0..155 的话，其余三列四分之三的文字都留着英文，悬停/选中必然穿帮。
处理方式：**4 列 × 9 行全部汉化**，`FLOWCHART` 沿用同任务 `radio_button` 表里
已定稿的「流程图」，不自创文案；箭头与 y≥400 的纸张/白块/棕块/三角按钮/NO. 输入框
全部写进「不能碰」清单并逐像素核对。

这类偏差本项目出现过四次（`frame_text` 尺寸、`index` 的 RESET 空行、
`frame_manual` 鼠标行位置、这次的列数行数）。**文档给文案，文件给几何**；
有冲突按文件做，并在交付时把差异列给用户看，不要默默改文档或默默照抄文档。

### 11.2 先做「多状态差分」，能省掉一半工作

拿到多状态雪碧图，第一步不是逐格量文字，而是**把相邻状态列/行逐像素相减**：

| 图 | 差分结果 | 推论 |
|---|---|---|
| `radio_button` 三列 | 文字层 32550 像素里只有 701 个不同 | 三列文字逐像素相同，差异只在左侧圆形图标颜色（深青 / 亮青 / 金） |
| `check_box` 三列 | 67500 里只有 1118 个不同 | 同上，差异只在方框图标 |
| `sys_quit` / `sys_back` 三行 | **alpha 总和完全相同**（708.0k / 行），RGB 中位不同 | 三行是同一套 alpha 场，只是辉光色不同：深青 → 亮青 → 青白 |
| `popup_parts` 四列 | 列2 vs 列3 的 alpha 形状 IoU 0.992，列0 vs 列1 只有 0.275 | 列2/3 近乎重复；列0 是另一套禁用态样式 |

于是：radio/check **一套中文图层复制三列**，sys **一套字形按行换辉光色**，
只有 popup 需要逐列配色。这既省事，也天然保证状态切换时字形不跳动。

反过来，如果差分发现各状态**字形本身**不同（比如按下态字重变粗、有位移），
就不能复用，必须逐行单独渲染并分别验收。

### 11.3 用 alpha 分层校准，别凭观感调 gain

这轮最有效的一个习惯：把原图和成品在文字带里的 alpha 分成五档打印出来。
汉字笔画密度和拉丁字母完全不同，凭「看着差不多」调参几乎必然过实或过虚。

`popup_parts` 第 2 行 SAVE 实测（每格 171×36）：

| | >=200 | 100~200 | 20~100 | alpha 总和 |
|---|---|---|---|---|
| 原图列 0（禁用） | 0 | 0 | 1020 | 55.4k |
| 第一版成品列 0 | 541 | 55 | 45 | 146.8k |
| 原图列 1/2/3 | 283 | 527 | 687 | 183.5k |
| 第一版成品列 1 | 979 | 92 | 647 | 289.9k |
| 定稿成品列 0 | 0 | 0 | 619 | 55.3k |
| 定稿成品列 1 | 473 | 513 | 59 | 180.8k |

第一版把禁用态画成不透明亮字（亮了近 3 倍）、把常态画成实心米白块（超 60%）。
定稿靠三个量把它拉回来：禁用态整层 `alpha × 0.38`、常态 `× 0.90`、
字距从 1 拉到 4。数字不必逐档命中，但**总和量级必须对齐**。

`sys_quit` 同理：原图每行 `>=210:864 / 140~210:984 / 60~140:2455 / 20~60:1880 / 总 708k`。
第一版用 MaxFilter 外扩 + gain 0.62，做出 `140~210:3303 / 总 963k`——
就是那块青色矩形板；收紧后 `140~210:387 / 总 282k`——光又整个消失；
定稿用整行小半径模糊 + gain 1.75，得到 `140~210:618 / 60~140:1902 / 20~60:1902 / 总 499k`，
肉眼看是柔和包字的一圈青光，没有直边。

### 11.4 这一轮新踩的八条坑

1. **衬线/宋体细笔画在小字号下会「发灰」。**
   `radio_button` 用 SimSun 19px，白字实像素（alpha>200）只有 49，原图 251，
   合成到深底肉眼就是灰字。原因不是颜色设错（RGB 实测就是 255），而是细横画
   抗锯齿后 alpha 只有 ~120。解法：文字层 alpha 乘 1.75 再 clamp，把中间调推到 255；
   实测升到 172，视觉与原文同档。这条和 10.4「白字别用 1px 描边」是同一类问题。

2. **多状态列里，「状态差异」可能根本不在文字上。**
   一开始容易下意识给三列各配一套颜色/亮度，结果反而破坏了原图。
   先差分（11.2），确认差异只在图标或辉光色，再决定复用。

3. **汉字是方块字，MaxFilter 外扩 + 描边 + 宽辉光会把字间填满成矩形色板。**
   这正是用户在第一组图里批评过的观感，换了图又复发了：`popup_parts` 第一版
   每个中文词后面都有一块亮白/亮红矩形，`sys_quit` 每格是一块青板。
   三个动作一起才解决：**拉字距（1→4）、去掉 MaxFilter 外扩改成直接对字形
   做小半径高斯模糊、发光 alpha 做幂次压缩或按原图总量缩放**。
   拉丁字母笔画稀疏，同样的外扩参数不炸；中文一用就炸。

4. **禁用态是「半透明暗字」，不是「暗颜色的实字」。**
   原图列 0 所有像素 alpha <100，第一版按 `fill=(196,179,160)` 画成 alpha=255，
   看起来比原图亮 3 倍。状态差异经常体现在 **alpha** 上而不是 RGB 上，量的时候
   一定要连 alpha 一起分层统计。

5. **中文字数 × 字号必须小于格宽，否则溢出、裁切、串格。**
   `sys_quit` 词格宽 83px，第一版用 22px × 4 字 = 91px，「退出游戏」直接冲进
   相邻格被裁掉，还和「返回标题」连成一片。收到 19px（76px）后正常。
   画之前先算一遍：最长词字数 × 字号 + 字距 < 格宽 − 余量。

6. **按词格分别裁剪辉光，会把光切断在格边界。**
   `sys_quit` 改成 19px 后字不溢出了，但三行退化成纯白字、完全看不出青光梯度。
   原因是每个词单独生成 patch，模糊在格边被裁。改成**整行一个图层**
   （249×38）统一渲染再统一模糊，光可以自然跨过词间空隙，梯度立刻回来。

7. **「残留旧字」的检查口径很容易误报，别用「成品里还有没有白字」判断。**
   中文也是纯白 `(255,255,255,255)`，笔画交叉处会与原英文像素逐像素巧合相同
   （radio 5.6% / check 6.4%）。而且清除区已清成 alpha=0，区内任何不透明像素
   只可能是新中文——逻辑上不可能残留。
   正确判据改成「**原图文字像素 100% 落在清除区内**」，这才是能防住
   「整格漏擦」的那一条。

8. **图标高光会被当成文字。**
   写完上面的覆盖检查，radio 报漏擦 1183 像素、popup 报 248，定位后发现分别是
   金色图标里的近白像素（x 375~425）和红色箭头的高光（x 433~467 / 649~683）。
   阈值检查要带 **x 范围限定**，只统计文字列，别把装饰资产的亮像素算进来。

### 11.5 三种渲染模型，按图挑

| 模型 | 用在 | 关键点 |
|---|---|---|
| 纯白衬线字 | `radio_button` / `check_box` | 宋体配原图拉丁衬线 / 日文明朝体；alpha 加权加实；三列复用；左对齐照抄原文字左沿 |
| 细斜体三层字：暖白柔光 / 半透明字身 / 1px 细色描边 | `popup_parts` | **描边最实、字身半透明、柔光面积最大**（照原图 alpha 分层）；宋体配衬线斜体；逐字基线递升 + 整层斜切复现倾斜；四列各自配色；禁用态只靠柔光堆面积，峰值 <120 |
| 白字 + 青色外发光 | `sys_quit` / `sys_back` | 原图 RGB 模型极简：alpha≥210 纯白，其余全是单一青色。所以「青光层 + 白字层」两层合成即可，三行只换青色；对齐按原图墨迹中心 |

`popup_parts` 这一行最初写的是「白字 + 下层描边 + 轻微倾斜（shear 0.16）」，
被用户连点四个问题后整体返工。**那不是调参能救的，是模型选错了**——
完整量测与决策过程见 11.8，别照抄这里的早期描述。

### 11.7 什么时候该停下来问

### 11.8 返工案例：用户说「字变正了 / 太粗 / 红白反了 / 位置偏左」

一次交付后收到四条反馈，全部指向同一类盲区：**前面几轮把「颜色和位置」量得很细，
却把「字形、层序、重心」交给了直觉。** 这四条值得单独记，因为换任何一张斜体艺术字图
都会再遇到。

> 反馈原文：「原图是斜着的，但是你汉化后的变成正的了」「字体太粗，美术风格和
> 原图差距有些大」「原图是红字，白色发亮，你变成了白字，红色描边」
> 「最佳效果已经是对应居中……返回标题微微靠左，退出游戏靠左很多」

#### 先量，四个数字把争论变成事实

| 量什么 | 怎么量 | 原图 | 返工前 |
|---|---|---|---|
| 整行基线倾角 | 对墨迹像素做加权 PCA 取主轴 | −5.4° ~ −7.0° | −0.4° ~ −2.1° |
| 字形斜度 | 逐行墨迹质心对 y 拟合 `dx/dy` | −1.77 | −0.20 |
| 笔画实度 | alpha>200 的像素数（SAVE 行每列） | 289 | 901（3 倍） |
| 柔光面积 | 30<alpha<120 的像素数 | 675 | 91 |
| 每词墨迹中心 | alpha>180 的包围盒中心 | 44.5 / 129.5 / 208.0 | 41.5 / 124.5 / 207.0 |

`dx/dy` 那个 −0.20 是关键：配置里明明写了 `shear=0.16`，但中文方块字轻微斜切
在视觉上几乎读不出来，用户看到的仍是正体。**「代码里有倾斜」不等于「看起来是斜的」，
要用原图和成品的同一个量来做差。**

#### 四条决策，都不是调参

1. **倾斜拆成两件事。** 原图既有整行左下→右上的基线倾角（PCA 量），也有字母
   本身的斜体。中文用「逐字基线递升 `rise`」复现前者、「整层斜切 `shear`」复现
   后者；只加大 shear 会把方块字拉歪，只递升会变成阶梯。定稿后 PCA 到
   −5.2° ~ −9.7°，和原图同一量级。
2. **换字体族，不是换字号。** 粗黑体 `msyhbd` → 常规黑体 → 宋体，做了同参数
   并排图。原图是衬线斜体，宋体横细竖粗、末端有顿角，明显最贴。
   **「太粗」很多时候是字重和字体族选错，把字号调小只会让字更糊。**
3. **层序反推，别信「字应该是实心的」。** 原图高 alpha 的 289 个像素居然是
   **描边**（列1 深褐 / 列2 红 / 列3 橙红），字身是 120~200 的半透明暖白，
   柔光是最淡但面积最大的暖白。旧版把字身画成 255 实心、描边做粗、柔光几乎没有，
   于是白块吃掉红色，红白观感整个反过来。改成「柔光 → 半透明字身 → 1px 细描边」
   后红色重新成为最实的一层。顺带把常态描边色从自定的 `(36,22,24)` 换成
   原图实测中位 `(69,55,52)`，米白字身才不再发灰。
4. **对齐基准换成墨迹中心。** 词格是引擎切的（83px 一格），跟字的重心没关系。
   在 config 里直接写逐格量出的 `centers=[44.5, 129.5, 208.0]`，`x = center - tw/2`。
   修完误差 0 / −0.5 / −2px。
   ⚠️ 复核中心时**别用整个格子的 min/max**：相邻词右沿溢出 0.5px 就会把
   `min` 拉走，测出「返回偏左 13.5px」的假象。按 x 投影找连通块、按块算中心。

#### 校准节奏（这轮真正省时间的地方）

先固定结构（层序、字体、倾斜方式），再对 `glow_blur / glow_gain / body_gain`
做小网格扫描，用「核心 / 中层 / 光晕 / 总 alpha」四档与原图的相对误差打分，
挑误差最小的一组，而不是一轮轮凭眼睛调 gain。宋体比黑体细，换字体后要**重新扫描**，
直接沿用黑体的 gain 会整体偏淡。

两个从扫描里学到的边界：

- 数据达标不等于视觉达标。`blur=6.0` 的分层数字和 `blur=5.0 / gain=2.8`
  几乎一样好，但前者会把字间 4px 空隙糊成一团雾板（用户批评过的老毛病）。
  **半径必须和字距一起看**，宁可小半径 + 高强度。
- patch 的左界要**严格等于清除区左界**，文字起点用 `text_x - clear_x0`。
  柔光半径一大，光就会往左溢出；若 patch 贴得比清除区更左，`清除区外 0 改动`
  立刻报错。这样裁切只发生在清除区内部，安全。

#### 结果与残留

定稿：SAVE 行每列总 alpha 188k（原图 183k）、禁用态峰值 115（原图全 <120）、

## 12. 给下一个接手者的一句话

**这份工具包不是复现公式，是一份「怎么少走弯路」的判断手册。**

接手新图时：先读 0.1 的五问和 0.2 的路线表，把图归类；
再量 alpha、逐格量底色字色、量原文字对齐与发光剖面；
把不能碰的装饰写成配置；按路线选清除和补底；最后 1:1 验收，
出问题就查 0.3 症状速查回退。

具体纪律：有底板就补真实纹理，透明叠加层只清文字带、别碰装饰；
对齐照抄原图，别用习惯；清除要整块、辉光按原图 alpha 剖面来并挖空字核心、
白字别用 1px 描边；原图没有的装饰一律别加，拿不准就量剖面；
**颜色、阈值逐格量，别按行号或状态名假设**；
**先做多状态差分**，能复用就别画 N 遍；
**汉字是方块字**，字距、字号×字数、外扩半径都要按中文重新算；
**文档给文案，文件给几何**，冲突时以文件为准并把差异告诉用户。

第 0 节的决策树、第 3 节的判据、第 4 / 10.4 / 11.4 节的弯路、
第 8 / 10.7 / 11.6 节的流程是可以带走的；脚本里所有数字都只是这三组图的答案，
换图请重新量。剩下的是审美，按原图的重量感去靠，不必跟这份文档的数值较劲。
